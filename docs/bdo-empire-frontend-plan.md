# bdo-empire 纯前端融合方案

分析日期：2026-10-10。运行约束：保持 Vue/Vite 静态网站，不增加 Python 服务。

## 建议

迁移 bdo-empire 的建模逻辑到 JavaScript，使用 HiGHS WASM 求解，并把收益预计算、建模和求解放进 Web Worker。新增“帝国优化”页面，先预览方案，再由用户应用到现有工人管理界面。

这项工作属于优化模型迁移。原项目的 Python、rustworkx、highspy 和桌面 GUI 不能作为现有 Vue 项目的直接依赖运行。浏览器版复用的是模型与业务规则，运行时使用 JavaScript 和 WASM。

## 能力边界与关键差异

bdo-empire 联合选择采集点、工人所属城镇、连接节点和住宿容量，以给定贡献点预算下的收益为目标。现有 bdo-noderouter 为已确定的任务寻找连接；新增优化器负责决定任务和配置。两者可以保留在同一个产品里。

原实现使用 40 级平均属性工人和技能优化候选，默认收益最高的城镇候选数为 6、路径中间节点的近邻城镇数为 7。原模型不优化工作坊利润，仓库采用零成本假设，基地扩展主要固定已有采集点与城镇配对。[入口和默认配置](https://github.com/Thell/bdo-empire/blob/v0.8.2/src/bdo_empire/main.py)、[模型约束](https://github.com/Thell/bdo-empire/blob/v0.8.2/src/bdo_empire/optimize_highspy.py)。

需要分别处理以下差异：

1. **理论工人与实际工人。** 第一版可以生成平均属性工人的建设方案；使用玩家实际工人、现有技能和有限工人数，需要增加逐个工人的分配约束，不能仅把现有工人 JSON 作为输入就宣称已支持。
2. **资源浮动。** 上游收益计算使用单个地区修正值；本项目还支持浮动资源分布。浏览器版应采用本项目计算口径，保证优化预览与应用后收益一致。[上游收益计算](https://github.com/Thell/bdo-empire/blob/v0.8.2/src/bdo_empire/generate_value_data.py)。
3. **价格与单位。** `marketStore.prices` 已包含自定义价、税率、自用物品和组合价格规则，不能再次扣税。现有 `priceDaily` 单位为百万银币/日，上游候选收益为银币/日，应在适配层明确转换。
4. **贡献点预算。** 节点成本、住宿成本、仓库成本、工作坊、自定义任务和围栏成本需要分别列出。节点与住宿预算不等于整个账号的总预算，已有固定节点也不能重复扣除。
5. **数据来源。** 必须使用当前网页的数据快照。本次比较发现双方工人、技能和距离数据一致，但 370 个采集点中有 25 个掉落记录不同；节点数据结构和部分连接列表也不同。住宿表字段存在差异，但共同城镇的容量—成本曲线一致。不能直接复制上游数据包覆盖本项目。
6. **最优性表述。** gap 是当前模型、候选范围内的求解差距。候选裁剪、理论工人和仓库假设会限制结论，页面不应宣称得到全游戏全局最优。原模型中的经验性最少采集点约束也应单独评估，不直接当作业务要求迁移。

## 推荐架构

```mermaid
flowchart LR
  A[优化页面：预算和约束] --> B[冻结数据与设置快照]
  B --> C[Web Worker：计算候选收益]
  C --> D[构建稀疏整数规划模型]
  D --> E[HiGHS WASM]
  E --> F[当前最佳方案与求解差距]
  F --> G[预览、校验与应用]
  G --> H[现有工人列表与地图]
```

建议模块：

| 计划模块 | 职责 |
|---|---|
| `src/views/EmpireOptimizerView.vue` | 设置预算、展示状态与方案差异 |
| `src/stores/optimizer.js` | 管理 Worker、输入快照、最佳方案与应用状态 |
| `src/optimizer/snapshot.mjs` | 从现有状态提取普通对象，记录数据版本和约束 |
| `src/optimizer/values.mjs` | 候选工人、技能和收益计算，复用本项目口径 |
| `src/optimizer/graph.mjs` | 统一节点 ID、连接方向、候选范围与特殊节点规则 |
| `src/optimizer/model.mjs` | 输出稀疏矩阵、变量索引和约束元数据 |
| `src/optimizer/solve.worker.mjs` | 初始化 WASM、求解、回调与资源释放 |
| `src/optimizer/result.mjs` | 解析分配、节点、路径、住宿方案并独立校验 |

Worker 接收普通数据，不直接引用 Pinia/Vue 状态。开始优化时冻结价格和参数；求解过程中市场刷新不改变正在求解的问题。

建议输入至少包含：模式、预算及预算口径、节点和住房数据版本、有效价格、资源设置、固定节点、付费住宿、保留任务、求解时间限制和候选规模。

建议输出至少包含：候选工人/任务分配、选择的节点、每项任务的路径、住宿配置、成本分项、日收益、求解状态、最佳上界、gap、计算假设及输入版本。

## 建模与现有代码的衔接

核心模型继续使用上游的联合规划结构：

- 二元节点变量：节点被任意任务使用时只计算一次贡献点成本。
- 采集点—城镇分配变量：同一采集点最多分配给一个城镇。
- 住宿容量选择变量：每个城镇选一个容量档位，并满足工人与保留任务的住宿需求。
- 网络流变量：分配成立必须存在有效连接，强制节点通过相应规则连接。
- 收益目标与预算约束：收益由冻结的候选表决定，预算使用明确的成本分项。

先用小模型验证，再为完整模型使用 CSC/CSR 稀疏数组。LP 文本可以保留为调试输出；大模型不必经过长字符串构建和解析。[稀疏模型接口](https://github.com/lovasoa/highs-js#persistent-models)。

本项目已有可复用入口：

- `src/stores/market.js` 的 `prices`：有效价格。
- `src/stores/game.js` 的 `profitPzTownStats`、`src/stores/user.js` 的 `calcCyclesDaily`：采集收益口径。
- `src/gameLookups.mjs`：平均属性和距离索引。
- `src/stores/user.js` 的 `townInfra`：住房、仓储成本口径。
- `src/views/HomeView.vue` 的导入导出格式：工人和任务方案的兼容参考。

应把需要在 Worker 中使用的计算抽成纯函数，供界面和优化器共同调用，避免长期维护两套收益公式。

**必须保留求解出的节点和路径。** 当前 `routing.js` 会根据工人任务重新计算路径，现有 JSON 导入主要导入工人配置。仅导入生成的工人，会丢失求解器选择的连接方案；近似路由的成本可能变化。优化方案应独立保存 `selectedNodeIds` 和任务路径，在约束未变化时使用这些路径；用户修改相关任务或节点后再使方案失效。不要把优化连接节点混入刷怪节点列表来强行锁定。

应用前使用现有业务口径复算收益和总贡献点，检查节点可达、重复采集点、工人数、住宿容量、已保留任务和仓库成本。失败的方案停留在预览，不直接覆盖用户配置。

## 浏览器运行策略

- 只在进入优化页面或首次开始优化时加载 HiGHS，避免增加普通页面的首屏成本。
- 单个 Worker 承担收益预计算、图处理、建模和求解；先限制为一个任务，避免并发实例增加内存压力。
- 优先生成一个可行方案，再继续改进。页面显示已用时间、当前收益、贡献点分项、最佳上界与 gap；没有可信的固定百分比进度。
- 利用 `mipImprovingSolution` 回调保存新可行解，利用 `mipLogging` 回调更新统计；节流消息，不把完整模型或所有流变量反复发送给界面。
- **停止按钮不能仅依赖向 Worker 发消息。** 求解是同步调用，Worker 在求解结束前不能处理普通消息。首版可以用 `worker.terminate()` 立即停止，保留主线程已收到的最佳可行方案；尚无可行解时显示无方案。[同步回调及 Worker 说明](https://github.com/lovasoa/highs-js#callbacks)。
- 后续若需要合作式中断，可使用共享原子标志与中断回调，但需要额外处理浏览器跨源隔离与资源响应头。
- 正常完成后在 `finally` 中执行 `model.dispose()`；异常或强制停止后重建 Worker。
- 不直接沿用上游无限时长及原生并行设置。可设计约 30 秒和 2 分钟的时间上限预设，这些是允许计算的上限，不是达到某种质量的耗时承诺。
- 桌面浏览器先验证完整模型；移动端使用更小候选范围和更短上限。采集点/城镇限制会影响质量，需显示在方案信息中。

## 分阶段落地

### 第一阶段：验证核心模型

选择少量城镇和 20–50 个采集点，统一数据和价格输入，迁移节点选择、任务分配、住宿和流约束。检查结果可行性，并与上游在同一候选范围和计算假设下的结果对照。对照收益和成本，不要求存在多解时工人配置完全相同。

记录变量数、约束数、求解时间、gap、取消行为和峰值内存。完整浏览器性能结论应在这一步之后给出。

### 第二阶段：首个可用版本

- 平均属性工人的从零建设方案。
- 贡献点预算、固定刷怪节点、付费住宿、保留住宿和资源修正。
- 限时求解、停止并保留最佳方案、地图和成本预览。
- 方案导出、明确选择应用范围、应用前备份与校验。
- 先明确节点与住宿预算，仓库和其他用途的成本单列；若接受总预算输入，必须扣除保留成本，并在应用前复算，超预算方案不能直接应用。

先用本项目收益和数据口径生成完整可复核方案。收益表中标明理论工人假设，避免把建议招聘的工人混成玩家已有工人。

### 第三阶段：与玩家现状深度融合

- 用已有工人和实际技能优化任务，每个工人最多分配一次。
- 锁定部分工人、任务和节点，在保留现状的条件下扩展。
- 将指定仓库的物品种类与容量成本纳入模型，之后再考虑多仓库选择。
- 扩展种植、工作坊及其他任务；每项扩展需要相应收益、成本和约束，不仅是增加页面选项。
- 用现有可行配置作为初始解，缓存相同数据和约束下的候选收益。

## 工作量判断与验收

这是中等偏大的功能开发，主要成本在模型、收益口径、图约束和方案应用流程，页面本身只占一部分。不建议在完成小模型对照之前承诺完整功能耗时或浏览器性能。

首版最低验收：预算满足定义、固定节点可达、住宿不超容量、收益可复算、价格不重复扣税、停止能保留已收到的可行解、应用不丢失路径、不静默替换已有工人，并且 `/workerman/` 子路径下开发及生产 WASM 加载均成功。

## 实施进展（2026-10-10）

已实现首个浏览器版本：`/workerman/optimizer`。支持 20、50、100 或全部有有效价格的采集点候选，所选城镇内的平均属性工人技能候选、节点流连接、固定刷怪节点、Ancado、付费住宿、指定仓库容量与个人仓储预算。

页面支持收益与贡献点预览、节点连接示意、限时计算、停止保留可行方案、兼容首页的 JSON 导出、保留精确路径的直接应用与撤销。直接应用暂限仅有采集/空闲工人的帝国，实际工人和其他任务优化仍属后续阶段。

独立穷举验证覆盖不同预算、共享连接、住房/仓库联合成本与固定节点；实际数据验证收益口径与应用后的总贡献点。上游 Python 完整流程未直接执行对照，因此不宣称已与其所有默认剪枝和求解设置逐项等价。

模块、上游来源和测试命令见 [浏览器优化器说明](../src/optimizer/README.md)。

浏览器验证包含开发环境与生产 `/workerman/` 子路径的求解、应用、JSON 导出、刷新恢复、撤销及 390px 布局。全 370 个采集点候选、全部城镇的模型包含 68,849 个变量和 157,130 个约束，已验证初始可行方案与停止保留流程；测试使用固定行情，只用于验证功能和模型规模。
