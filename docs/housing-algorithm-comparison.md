# 普通城镇查表与逐栋住房求解对照

试算日期：2026-10-13。使用当前仓库的房屋数据、住房方案表和住房求解实现。

本次结果：32 个有房屋城镇、每城镇 8 组需求，共 256 组。116 组可行需求的查表成本与逐栋求解成本完全相同，且逐栋求解均证明最优；140 组双方均判定不可行。没有发现逐栋求解节省贡献点的样本。

建议维持当前混合方式：普通城镇继续查表，自定义用途或工作工坊占用的城镇继续逐栋求解。当前证据支持查表的速度优势，没有支持将普通城镇全部改为逐栋求解能降低成本。这里的结果限于测试样本，未穷举所有需求，也未比较完整帝国的收益。

## 条件与方法

- 两种方法使用同一份 `houseinfo.json` 和 `all_lodging_storage.json`，不设置自定义用途、工坊占用或其他房屋限制。
- 需求均为房屋额外提供的床位和仓储格数，不是雇佣工人总数或包含免费容量的仓库总量。需求组为 `(0,0)`、`(1,3)`、`(4,25)`、`(8,50)`、`(12,80)`、`(20,120)`、`(1,184)`、`(40,0)`。
- 高仓储需求以基础仓储 8 格、无价值礼包/付费仓储的场景为例，房屋需求限制为 184 格，和每城镇 192 格总上限一致。实际使用按玩家的服务器、礼包和付费容量扣除。
- 查表执行当前 `game.lsLookup` 的原始函数，同时遍历整个表核对最低成本。256 组实际查表结果均与全表最低成本一致。
- 单城镇页面在无保留用途时也走查表路径。本次直接调用 `solveHousing`，绕过这个快捷路径，才能比较真正的逐栋房屋算法。
- 逐栋求解以住房贡献点最小为目标，按前置依赖、用途互斥、床位和仓储约束计算。初始时限 2 秒；普通有房屋城镇所有测试均在时限内证明最优或不可行。
- 所有可行房屋结果独立复核房屋用途、前置依赖、容量和成本。没有修改应用算法或玩家配置。

## 计算时间

本机 Node.js 22.22.0，使用与网页相同的 HiGHS 1.15.1 WASM。性能数字仅针对计算核心，包含逐栋模型构造和结果复核，不含浏览器绘制、数据加载或 Worker 启动。

- 可行需求查表平均约 **0.041 ms/次**，预热后重复 500 遍测量。
- 逐栋求解可行需求中位数约 **17.02 ms**，95% 分位约 **186.83 ms**，最慢约 **447.84 ms**。
- 逐栋求解全部 256 组需求中位数约 **2.30 ms**，其中大量不可行小城镇需求很快被拒绝。
- 首次加载 WASM 约 **77.78 ms**，没有计入上述逐次求解数字。

重复需求可通过页面缓存加快，实际浏览器耗时可能随设备和运行环境变化。

## 特殊边界与数据版本

原始试算还包含雷玛岛、奥基鲁阿之眼、贝兰迪尔三个没有可租房屋的查表城镇。这三个城镇产生零变量模型，当前逐栋求解封装没有返回正常的可行/不可行结果，因此 24 组空模型测试未纳入租房算法对比。现有页面通过查表处理它们。若以后将所有城镇强制改为逐栋求解，需要补齐零需求零成本、非零需求不可行的空模型处理。
